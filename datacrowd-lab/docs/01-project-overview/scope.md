## 1.3 Project Scope

Table 1.10. In Scope

| Feature | Description | Priority |
|---|---|---|
| Multi-tenant project lifecycle management | Clients create and configure projects with billing status, reviewersCount, rewardPoints, taskQuota, and minAnswerSeconds | Must Have |
| Asynchronous dataset ingestion via Go-Runner | CSV, JSONL, and ZIP (with manifest.jsonl) files parsed by a dedicated Go service; failed rows persist to Dead Letter Queue | Must Have |
| Atomic task distribution with SKIP LOCKED | Concurrent workers claim tasks without race conditions via PostgreSQL FOR UPDATE SKIP LOCKED | Must Have |
| Finite-state-machine task lifecycle | Task statuses (NEW → LOCKED → IN_REVIEW → APPROVED) enforced at the service layer; invalid transitions rejected | Must Have |
| N-of-M consensus review | Answer reaches APPROVED only after reviewersCount independent approvals; configurable per project | Must Have |
| Dynamic Trust Score anti-fraud subsystem | Trust Score per worker adjusted on every reviewer verdict; workers below 30 gated from new task assignment | Must Have |
| Honeypot task injection and bot detection | Pre-verified control tasks injected into the queue; automatic penalty for wrong answers or too-fast submissions | Must Have |
| Role-based access control (RBAC) | Four roles (CLIENT, WORKER, REVIEWER, ADMIN) enforced at JWT token, API Gateway routing, and service layers | Must Have |
| Database-per-service isolation | Three logical PostgreSQL databases (auth_db, core_db, payments_db) with no cross-database foreign keys | Must Have |
| Stateless JWT authentication | HS256 JWT tokens with configurable TTL; X-Internal-Token for service-to-service calls | Must Have |
| Mock and real Stripe billing integration | Stripe-compatible checkout session model; STRIPE_ENABLED flag toggles between mock and live Stripe | Must Have |
| JSONL and typed CSV dataset export | Verified answers exported with per-dataType column schemas; download via authenticated REST endpoint | Must Have |
| Containerized deployment via Docker Compose | Full system brought up with a single command; health checks, named volumes, and per-service Dockerfiles | Must Have |
| GitHub Actions CI/CD pipeline | Per-service build and test jobs; JaCoCo coverage gate; Docker image build on main branch | Must Have |
| ML pre-annotation via HuggingFace Inference API | Optional aiSuggestedLabel and aiConfidence fields in task payload generated by zero-shot classification | Should Have |
| Server-Sent Events for real-time progress | SSE endpoint streams project completion percentage to the client dashboard every 2 seconds | Should Have |
| Prometheus and Grafana observability | Custom Micrometer counters (tasks_submitted, tasks_approved, honeypot_failed, bot_detected); Grafana dashboard provisioned | Should Have |
| Caffeine in-memory caching | Worker stats (60 s TTL), available projects (30 s TTL), project public info (30 s TTL) cached to reduce DB load | Should Have |
| OpenAPI documentation via springdoc | Per-service Swagger UI; aggregated in Gateway; dual security schemes (bearerAuth + internalToken) | Should Have |

Table 1.11. Out of Scope

| Feature | Reason | When Possible |
|---|---|---|
| Production Stripe integration with live webhooks and PCI key management | Requires live Stripe account, webhook endpoint exposure, and PCI DSS compliance review — outside diploma project scope | Phase 2 (post-graduation) |
| Kubernetes deployment manifests and horizontal pod autoscaling | Requires cluster provisioning and Helm chart authoring — infrastructure work beyond the scope of the architecture validation | Phase 3 (production deployment) |
| Federated identity (OAuth2/OIDC, SAML, enterprise SSO) | Integration with external identity providers requires compliance review and is not needed for the diploma demonstration | Phase 2 |
| WebSocket real-time push notifications to workers | SSE is sufficient for the current progress monitoring use case; WebSocket adds stateful connection management complexity | Phase 3 |
| Native mobile applications (iOS / Android) | The frontend is a responsive web application; native apps require separate development teams and distribution pipelines | Out of roadmap |
| Proprietary annotation editors (bounding-box, audio waveform, code diff) | The JSONB answer format is flexible enough to accept such payloads; the rendering UI is out of scope | Phase 2 |
| Multi-region data residency and cross-datacenter replication | Requires cloud infrastructure contracts and data governance frameworks | Out of roadmap |

Table 1.12. Assumptions

| # | Assumption | Impact if Wrong | Probability |
|---|---|---|---|
| 1 | Workers operate the platform through a standard web browser on a desktop device | Mobile-specific layout defects; reduced accessibility | Low |
| 2 | Dataset files uploaded by clients are well-formed (valid CSV headers, valid JSONL lines for the majority of rows) | Increased DLQ (failed_items) volume; clients receive lower task counts than expected | Medium |
| 3 | The HuggingFace Inference API is accessible from the deployment environment when ML pre-annotation is enabled | Pre-annotation feature silently degrades to disabled mode; task payloads lack aiSuggestedLabel field | Low |
| 4 | PostgreSQL 16 is used as the target database version (SKIP LOCKED semantics, JSONB support) | Concurrent task assignment correctness cannot be guaranteed on older PostgreSQL versions | Very Low |
| 5 | JWT_SECRET and INTERNAL_TOKEN environment variables are set with values of at least 32 characters before service startup | Service startup fails with an explicit IllegalStateException — caught at launch, not in production | Low |

Table 1.13. Constraints

| Constraint Type | Description | Mitigation |
|---|---|---|
| Technology | Java version is fixed at 17 (LTS) per Spring Boot 3.4.1 parent POM | No mitigation required; Java 17 is fully supported through 2029 |
| Technology | Go version is fixed at 1.22 per go.mod | No mitigation required; Go 1.22 is a stable release |
| Architectural | The API Gateway is configured as permitAll for the diploma demonstration; JWT authorization is enforced inside each downstream service | This simplification is documented in the README; JWT enforcement inside services provides equivalent security guarantees |
| Deployment | The current deployment target is a single Docker Compose host; no container orchestrator is available | Stateless service design and named volume persistence ensure that migration to Kubernetes requires no code changes |
| Academic | The project must demonstrate all seven evaluation criteria (UX, Backend, Database, Microservices, Containerization, API Documentation, Automated Tests) within the scope of a bachelor project | Each criterion is addressed by a dedicated ADR in Section 2.4 |
| Financial | Live Stripe payments are not available in the demonstration environment | STRIPE_ENABLED=false activates the mock payment flow (/api/payments/mock/pay/{id}) which provides functionally equivalent behavior for evaluation purposes |
